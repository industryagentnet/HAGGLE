# HAGGLE-Expanded

**A scale-up extension of the HAGGLE benchmark — 500 feasibility-aware multi-issue commodity negotiation scenarios across five domains, preserving the original 68 published scenarios unchanged.**

> **HAGGLE-Expanded** extends [HAGGLE](../README.md) (v1.0, 68 expert-curated scenarios) to 500 scenarios by reusing the same 4-issue schema, value functions, and feasibility-aware metrics, adding 412 newly composed scenarios and two new commodity domains (**Chem** and **Copper**). The original `data/` directory is left byte-identical to the published v1.0 release; all new and carried-over content lives under `data_expanded/`.

## Overview

HAGGLE-Expanded is a non-destructive, backward-compatible extension of the HAGGLE benchmark for agent-to-agent (A2A) LLM bargaining over real Chinese B2B commodity procurement contracts. It keeps the v1.0 release untouched and adds a larger, programmatically generated scenario set that follows the exact same construction logic, issue structure, and evaluation protocol.

| Release | Directory | Scenarios | Domains | Status |
|---|---|---:|---:|---|
| **HAGGLE v1.0** (published) | `data/` | 68 | 3 (rebar, agri, coke) | unchanged, byte-identical to GitHub release |
| **HAGGLE-Expanded v2.0** | `data_expanded/` | 500 | 5 (rebar, agri, coke, **chem**, **copper**) | new |

Every commodity is balanced to an exact **90 feasible / 10 infeasible** split. Difficulty is derived from the ZOPA margin (`(budget − cost) / cost`): `>5% → Easy`, `2–5% → Medium`, `<2% or infeasible → Hard`. All 50 infeasible scenarios are `Hard`.

### Relationship to v1.0 (what changed, what didn't)

- **Preserved.** The 68 published v1.0 scenarios (`data/`) are **unchanged** — same IDs, same byte content, same `price_range` values (including the two expert-annotated nulls, see below). Anyone who pinned HAGGLE v1.0 sees no difference.
- **Carried over.** The 88 seed scenarios that seed `data_expanded/` (68 v1.0 scenarios + 10 chem + 10 copper pre-release seeds) keep their original IDs verbatim. IDs for newly composed scenarios continue from `max(original_id)+1` per commodity, so **no ID collisions** occur within any file.
- **Lightly repaired.** Two v1.0 scenarios — `rebar_scenario_008` and `rebar_scenario_014` — were feasible (`budget ≥ cost`) but had expert-annotated `expected_deal.price_range = null` in the published release. In `data_expanded/` these two `price_range` fields are repopulated with fair-deal regions consistent with the cost/budget anchors (`[3300, 3330]` and `[3100, 3150]` respectively). This is the **only** content difference between `data/` and the carried-over portion of `data_expanded/`; it lives in a separate directory so v1.0 stays intact.
- **Newly composed.** 412 scenarios generated by the expansion pipeline (see *Methodology*), spanning all five domains including the two new ones (chem, copper).

> **Why a separate directory.** Because the two repaired records make `data_expanded/` not byte-identical to `data/` for rebar, the expanded set is shipped as a sibling directory rather than overwriting the published `data/`. This keeps v1.0 reproducible while v2.0 is freely usable.

## Methodology

Scenarios are generated by `experiments/expand_data_v1.py` (seed `20260922`, fully deterministic and reproducible). The pipeline:

1. **Carry originals.** Load the 88 seed scenarios (the 68 v1.0 + 20 chem/copper seeds) and re-run `apply_rebuild` — idempotent on weights/numerics; repopulates feasible-but-null `price_range` records. Original IDs are preserved.
2. **Compose new scenarios** to reach 100 per commodity (90 feasible / 10 infeasible):
   - Sample `cost` and `first_ask` per commodity numeric band; `first_ask = cost·(1 + U(1%, 8%))`.
   - **Feasible**: `budget = cost·(1 + margin)`, `margin ~ U(0.5%, 8%)`; `target ~ U(cost, budget)`.
   - **Infeasible**: `budget = cost·(1 − gap)`, `gap ~ U(0.5%, 4%)`; `target = budget`.
   - Enforce strictly positive ZOPA width (≥1% of cost, ≥1 unit) on every **newly composed** feasible scenario, guaranteeing `target < budget` and `first_ask > target`.
   - Weights sampled from the 18 valid rank permutations of `{p, r, t, d}` (price is never rank-4); seller/buyer ranks are forced distinct. Strategy/context text assembled from per-commodity tactic pools.
3. **Assign IDs** continuing from `max(original_id)+1` per commodity; shuffle new scenarios; sort each file by ID suffix.
4. **Validate** (gate refuses to write on any failure): exactly 100 per commodity; exactly 90 feasible / 10 infeasible; unique IDs; all 16 schema keys present; `target ≤ budget`; `first_ask ≥ cost`; weight sums = 1 (±1e-9); seller/buyer rank permutations differ; feasible ↔ `price_range` non-null and within `[cost, budget]`; infeasible ↔ `price_range = null`.

Difficulty assignment: `Hard` for all infeasible and for feasible margin `< 2%`; `Medium` for `2–5%`; `Easy` for `> 5%`.

## Scenario schema

Identical to v1.0 — see the [HAGGLE README](../README.md#scenario-schema) for the authoritative field table. Each entry in `*_scenarios.json` has 16 fields:

`id`, `commodity`, `spec`, `quantity`, `seller`, `buyer`, `expected_deal`, `context`, `strategy_buyer`, `strategy_seller`, `difficulty`, `weights`, `weight_rank`, `w_S_true`, `w_B_true`, `weight_evidence`.

`commodity` is one of `rebar` / `agri` / `coke` / `chem` / `copper`. All other field semantics, the 4-issue structure (`p` price, `r` prepay, `t` terms, `d` delivery), and the private-information convention are unchanged.

### Value domains (across all 500 scenarios)

| Issue | Domain |
|---|---|
| `p` price | real-valued CNY/ton (copper priced at 0.5 granularity; others at 1.0) |
| `r` prepay | 0.05 – 1.00 |
| `t` terms | 1 – 30 days |
| `d` delivery | 1 – 15 days |

## Evaluation metrics

Unchanged from v1.0 — see the [HAGGLE README](../README.md#evaluation-metrics) for the full per-issue value functions and feasibility-aware aggregation (`DR_f`, `u_N^f`, `u_P^f`, `TW^f`, `AR`, `FD%`). With v2.0:

- Utility metrics are computed over the **450 feasible** scenarios (×3 runs = 1350 runs).
- The false-deal rate `FD%` is computed over the **50 infeasible** scenarios (×3 runs = 150 runs), a 7× larger safety probe than v1.0's 7 infeasible cases.

## Intended use & limitations

- **Use**: larger-scale evaluation of multi-issue LLM negotiation agents, opponent-modeling research, feasibility-aware bargaining studies, and cross-domain generalization tests (now spanning ferrous / agriculture / energy / chemicals / metals).
- **Provenance split.** The 88 carried-over scenarios are domain-expert-annotated real procurement cases; the 412 newly composed scenarios are programmatically generated from curated, commodity-specific numeric bands and tactic pools. They share the same schema and value functions but differ in annotation origin — researchers may subset by `id` (carried IDs are the low suffixes per commodity) if they wish to evaluate on expert-annotated data only.
- The Chinese `context`/`strategy_*` fields reflect real commercial bargaining practice and may contain culturally specific heuristics; absolute utility magnitudes are calibrated per-domain and comparable within a commodity.

## Reproducibility

Regenerate the entire `data_expanded/` directory deterministically:

```bash
python experiments/expand_data_v1.py   # writes data_expanded/ + prints the per-commodity report
```

The script runs `write_expanded()` (which calls `validate()` before every write) and `report()` (re-validates on load). Any scenario failing the schema/feasibility/weight invariants aborts the build rather than emitting invalid data.
